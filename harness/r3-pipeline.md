# R3 — 파이프라인

```
[입력: 대상 화면명]
  S1 수집 (에이전트) ─▶ S2 분석 (에이전트) ─⏸G1─▶ S3 설계 (에이전트) ─⏸G2─▶
  S4 제작 (사람, Figma · ⏸G3 협의 확정) ─▶ S5 검토 (에이전트) ─▶ [완료]
```

## 단계

| 단계 | 담당 | 원래 흐름 | 하는 일 |
|---|---|---|---|
| S1 수집 | 에이전트 | 1 | uibowl에서 대상 화면의 레퍼런스를 모은다 |
| S2 분석 | 에이전트 | 2 | 레퍼런스에서 우리 서비스에 반영할 부분을 뽑는다 |
| S3 설계 | 에이전트 | 3 | 화면 설계 문서를 쓴다 |
| S4 제작 | 사람 | 4·5·6 | Figma 키스크린 → 협의 확정 → 토큰·컴포넌트 → JSON 내보내기 |
| S5 검토 | 에이전트 | 7 | Figma JSON이 `design.md`·`story-service.md`를 위반하지 않는지 검토 |

## 입출력

| 단계 | 입력 | 출력 |
|---|---|---|
| S1 | 대상 화면명 | 레퍼런스 목록 (JSON: `app`, `ui_url`, `screen_type`, `note`) |
| S2 | 레퍼런스 목록 + `prd.md` | 분석 문서 (섹션: 반영할 것 / 반영하지 않을 것 / 근거 `ui_url`) |
| S3 | 분석 문서 + `prd.md` + `story-service.md` | 화면 설계 문서 (섹션: 목적 / 사용자 / 구성 요소 / 상태 / 권한) |
| S4 | 화면 설계 문서 + `design.md` | 승인 기록 (`figma_url` 포함) — R8에서 변경 |
| S5 | 승인 기록의 `figma_url` → 오케스트레이터가 Figma MCP(읽기 전용)로 변환한 JSON + `rules.json` | 검토 결과 (위반 목록 JSON + 요약) |

- S2의 모든 "반영할 것" 항목은 근거 `ui_url` ≥ 1
- S3은 5개 섹션 모두 존재

## 되돌아가는 지점

| 실패 | 복귀 |
|---|---|
| G1 실패 | S2 재작성 (원인이 레퍼런스 부족이면 S1) |
| G2 실패 | S3 재작성 |
| S5 `design.md` 위반 | S4 (사람이 Figma 수정) |
| S5 `story-service.md` 위반 | S3 (설계 수정) |

- 같은 단계 재시도가 2회를 넘으면 멈추고 사람에게 묻는다.

## S4 → S5 전환

- 승인 기록 파일이 G3를 통과(`approved: yes` + `figma_url` 포함)하고, 사람이 "검토해줘"라고 말하면 S5 시작. (R8에서 변경)
- G3 미통과면 시작을 거부한다.
